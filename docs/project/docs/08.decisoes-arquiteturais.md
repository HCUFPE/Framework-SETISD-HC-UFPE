# Registro de Decisões Arquiteturais (ADR)
## Sistema de Gestão Digital da Anatomia Patológica (UACAP)

Este documento registra as decisões arquiteturais críticas tomadas durante o design e desenvolvimento do sistema de rastreabilidade física da anatomia patológica, detalhando o contexto, a escolha técnica e as implicações de cada uma.

---

### ADR 001 — Adoção da Stack Técnica e Interface Híbrida Flexível

* **Status**: Aprovado
* **Contexto**: O laboratório opera em ambiente de bancada com fluxo majoritariamente manual (80%). Os técnicos lidam com amostras físicas e precisam de agilidade. Como a implantação de hardware de automação (impressoras e pistolas de QR Code) será gradual e passará por transição, o sistema não pode ser refém da presença obrigatória do leitor em todas as etapas, exigindo telas reativas que aceitem comandos rápidos tanto por hardware quanto por digitação tradicional.
* **Decisão**: Adotar a stack padronizada do framework *appstart* (Vue 3 + Vite no Frontend; Python + FastAPI no Backend; PostgreSQL local) e projetar uma **interface híbrida**:
  * O sistema contará com uma **aba ou funcionalidade dedicada exclusivamente para a leitura de QR Codes** quando o hardware estiver disponível.
  * Todas as rotinas mantêm campos alternativos de entrada manual (via teclado/clique) para busca e transição de status.
* **Justificativa e Impacto**: 
  * **Flexibilidade na Transição**: O sistema mitiga o risco de travar a operação do hospital enquanto as impressoras e pistolas novas não chegam ou não estão distribuídas em 100% das bancadas.
  * O Vue 3 garante que, ao bipar na aba de leitura ou ao digitar um código, a tela atualize seus componentes na hora (reatividade), sem necessidade de recarregar a página.

### ADR 002 — Integração Unidirecional de Consulta (Read-Only) via Anti-Corruption Layer (ACL)

* **Status**: Aprovado
* **Contexto**: O AGHU é o sistema mestre e independente do hospital e continuará sendo utilizado em paralelo pela equipe. O novo sistema precisa apenas extrair dados demográficos e números de solicitações para iniciar o rastreamento na bancada. Como o AGHU é um sistema externo e intocável, nossa aplicação não pode realizar nenhuma operação de escrita ou alteração nele.
* **Decisão**: Configurar a integração com o AGHU como sendo estritamente **unidirecional e de leitura (Read-Only)**, isolada em um *Provider* que atua como Camada Anticorrupção (ACL). O usuário insere um identificador do AGHU (ex: sequência de números do paciente/exame) e o sistema busca os dados para iniciar o fluxo local.
* **Justificativa e Impacto**:
  * **Independência de Sistemas**: Garante que os sistemas rodem em paralelo sem acoplamento de escrita. O sistema local atua como um auxiliar e automatizador do processo físico sem interferir na base de dados do hospital.
  * **Segurança de Domínio**: Protege o modelo local contra mudanças na API de consulta do hospital.

### ADR 003 — Escopo Negativo: Proibição de Escrita e Consultas SQL Diretas ao AGHU

* **Status**: Aprovado
* **Contexto**: Para garantir a segurança e a governança de TI do hospital, o ecossistema do AGHU deve ser tratado como uma caixa preta de consulta. Qualquer tentativa de conexão direta ao banco de dados ou envio de dados de modificação (escrita) quebraria os protocolos de segurança hospitalar.
* **Decisão**: Definir como um *Guardrail* inegociável (Escopo Negativo) que o backend **nunca fará consultas SQL diretas** e **nunca enviará dados de modificação/escrita para o AGHU**. Toda e qualquer interação limita-se ao consumo de **endpoints HTTP/REST de consulta** homologados pela TI do hospital.
* **Justificativa e Impacto**:
  * Alinhamento total com as políticas de governança hospitalar (o sistema local é um consumidor de dados, não um modificador).
  * Elimina o risco de impactos colaterais no sistema principal do hospital durante a automação das bancadas da UACAP.

### ADR 004 — Resiliência Operacional via Cache Local Estratégico

* **Status**: Aprovado
* **Contexto**: Uma queda temporária de rede ou indisponibilidade do link com o hospital paralisaria completamente a recepção de peças e o processamento de amostras se o sistema dependesse 100% de chamadas em tempo real ao AGHU.
* **Decisão**: Implementar um mecanismo de **Cache Local Estratégico** persistido no PostgreSQL local. No momento em que a triagem/recepção consulta uma solicitação do AGHU, os dados demográficos mínimos do paciente e do exame são imediatamente persistidos na base local.
* **Justificativa e Impacto**:
  * **Tolerância a Falhas**: Garante a resiliência operacional da unidade (UACAP). Se a rede cair, os técnicos conseguem continuar movendo as amostras (frascos, cassetes, blocos, lâminas) e realizando a macroscopia usando os dados armazenados localmente.

### ADR 005 — Modelo de Persistência Hierárquica Estrita para Amostras

* **Status**: Aprovado
* **Contexto**: O coração do laboratório é o controle físico. Uma única peça cirúrgica gera múltiplos fragmentos, que geram blocos de parafina, que por sua vez geram lâminas microscópicas. O banco de dados precisa garantir a integridade absoluta dessa árvore genealógica.
* **Decisão**: Modelar o banco de dados local refletindo rigidamente a árvore física do laboratório através de relacionamentos de chave estrangeira (`FRASCOS` -> `CASSETES` -> `BLOCOS_PARAFINA` -> `LAMINAS`). 
* **Justificativa e Impacto**:
  * **Rastreabilidade Total**: Garante que nenhuma lâmina exista sem estar vinculada a um bloco, impedindo inconsistências ou perda de rastreabilidade de subprodutos biológicos.
  * Adota políticas de integridade referencial estritas (`RESTRICT` para evitar deleções acidentais que deixem órfãos na árvore).

### ADR 006 — Suporte a Hardware de Automação via Emulação Nativa (Modo HID)

* **Status**: Aprovado
* **Contexto**: Leitores de código de barras e QR Code (pistolas de bancada) costumam exigir a instalação de drivers específicos ou middlewares proprietários em cada máquina do hospital, o que geraria um custo de suporte técnico imenso para a equipe de TI e engessaria as bancadas que ainda não possuem o equipamento.
* **Decisão**: Adotar e suportar exclusivamente leitores que funcionem em modo **HID (Human Interface Device)**. Nesse modo, o leitor emula um teclado virtual nativo, injetando o código lido diretamente no campo de texto focado na aba de leitura do sistema.
* **Justificativa e Impacto**:
  * **Transparência de Entrada**: Como o leitor emula um teclado, para a arquitetura do backend é indiferente se o texto do QR Code veio de um "bip" da pistola ou se o usuário digitou o número na mão por contingência. 
  * **Zero Configuração**: Qualquer máquina do hospital pode receber uma pistola sobressalente instantaneamente via USB sem precisar que a TI instale softwares adicionais.

### ADR 007 — Arquitetura de Notificação Assíncrona via WebSockets

* **Status**: Aprovado
* **Contexto**: Operadores em diferentes estações (triagem, macroscopia, microscopia) precisam visualizar atualizações de filas e alertas de prioridade (como exames de urgência) em tempo real, sem a necessidade de atualizar a página manualmente (*polling* constante).
* **Decisão**: Utilizar conexões bidirecionais baseadas em **WebSockets**, gerenciadas nativamente pelo FastAPI no backend e consumidas pelo Vue 3 no frontend.
* **Justificativa e Impacto**:
  * Otimiza o uso de banda da rede hospitalar, reduzindo o volume de requisições HTTP desnecessárias.
  * Provê uma experiência fluida para as filas de trabalho, onde um item liberado na macroscopia aparece quase instantaneamente na tela do técnico de processamento.
