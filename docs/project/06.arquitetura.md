# Arquitetura e Segurança

## 1. Stack Técnica (Baseado no Framework appstart)

A stack do projeto segue estritamente o modelo definido pelo appstart e não muda:

- Front-end: **Vue 3** com **Vite** e **TypeScript**.
  - Interface reativa, componente SPA e carregamento rápido.
- Back-end: **Python** com **FastAPI**.
  - Rotas assíncronas, alta performance e extensibilidade.
- Banco de Dados: **PostgreSQL**.
  - Persistência local das peças físicas, rastreabilidade e cache local.

## 2. Integração e Padrões Arquiteturais

### Arquitetura de Provedores

A aplicação utiliza uma camada de providers com interfaces e injeção de dependência.

- Cada domínio (pacientes, exames, frascos, cassetes, blocos, lâminas, impressoras) é acessado por meio de providers.
- A integração com o AGHU legada está isolada em um provedor específico.
- Esse provedor atua como **Anti-Corruption Layer (ACL)** para proteger o modelo local de mudanças e inconsistências do AGHU.

### Cache Local Estratégico

- Dados demográficos do paciente retornados do AGHU na triagem são cacheados no PostgreSQL local.
- O cache local garante que a UACAP continue operando mesmo com indisponibilidade temporária da rede do HC.
- O modelo de cache contempla:
  - paciente
  - exame
  - número de solicitação
  - dados clínicos mínimos necessários para visão unificada

### Mensageria

- Uso de **WebSockets** no FastAPI para notificações assíncronas.
- Essa mensageria é empregada para tráfego de pedidos de "Retrabalho" do patologista para a bancada técnica.
- Notificações em tempo real permitem que a equipe técnica receba alertas imediatos sem polling agressivo.

## 3. Conformidade LGPD e Acessos

### Autenticação Híbrida

- Suporte nativo ao **Active Directory (AD)** em produção.
- A autenticação é unificada com as credenciais dos profissionais do hospital.
- O backend valida permissões e emite tokens JWT para o frontend.

### Auditoria Rígida

- Todas as consultas aos dados de prontuário e dados clínicos importados do AGHU são auditadas.
- Logs de auditoria registram:
  - usuário
  - ação
  - timestamp
  - IP de origem
  - tipo de recurso consultado
- A movimentação de peças físicas e transições de estado também são registradas em trilhas de auditoria.

## 4. Guardrails para IA (SDD)

### Escopo Positivo (O que fazer)

- Seguir estritamente a divisão `routers -> controllers -> providers` definida pelo framework appstart.
- Manter separação clara entre rotas, lógica de negócio e acesso à persistência ou APIs externas.
- Criar rotinas de validação no fluxo de leitura da pistola de código de barras:
  - validação do formato do QR Code
  - autenticação do item
  - registro de leitura
  - tratamento de erros e feedback ao usuário

### Escopo Negativo (O que NÃO fazer - Anti-Patterns)

- **Não usar consultas SQL diretas contra o banco de dados do AGHU.**
- O backend deve sempre consumir os **endpoints HTTP** disponibilizados pela TI do hospital para acessar dados legados.
- Evitar vazamento de lógica AGHU para dentro do modelo local.
- Não expor detalhes de implementação interna do AGHU no frontend ou em logs acessíveis.

## 5. Observações Gerais

- A arquitetura segue a stack do appstart sem mudanças estruturais.
- O modelo local dá prioridade à **resiliência operacional** e ao **tratamento assíncrono**.
- A segurança é construída sobre autenticação AD, tokens JWT e auditoria detalhada.
- O design de integração garante que o AGHU seja tratado como um sistema externo controlado, sem dependência de consultas diretas ao seu banco de dados.
